# Aiken Quickstart

Aiken is a modern, statically typed language for Cardano smart contracts that compiles to Plutus Core, the code the ledger actually executes during validation. It matters because one toolchain covers the whole on-chain loop: writing validators, testing them with execution-unit reports, and producing the blueprint (`plutus.json`) that off-chain code and cardano-cli consume. This page sets up that loop on your machine.

## What Aiken is

Aiken source files (`.ak`) are compiled to Untyped Plutus Core and run inside transaction validation under a strict memory and CPU budget. The language gives you pattern matching, custom types, modules, built-in unit and property tests, and a standard library — all designed around the constraints of on-chain execution.

## Install

The recommended route is `aikup`, a small version manager for the Aiken toolchain. As of writing, the official instructions (https://aiken-lang.org/installation-instructions) are:

| Route | Command |
| --- | --- |
| npm | `npm install -g @aiken-lang/aikup` |
| Homebrew | `brew install aiken-lang/tap/aikup` |
| curl (Linux/macOS) | `curl --proto '=https' --tlsv1.2 -LsSf https://install.aiken-lang.org \| sh` |
| PowerShell (Windows) | `powershell -c "irm https://windows.aiken-lang.org \| iex"` |

After installing `aikup`, run `aikup` to fetch the latest Aiken release. Verify the binary you actually got:

```bash
aiken --version
aiken --help
```

Install methods and version numbers change quickly; the official installation page and `aiken --help` are the authority.

## Create a project

```bash
aiken new aiken-lang/hello-world
cd hello-world
```

Current documentation uses `aiken new <owner>/<name>`; some older tutorials show `aiken new <project_name>`. Check `aiken --help` for the syntax your version expects. The command scaffolds the project and already adds the standard library to `aiken.toml`.

## Project layout

| Path | Purpose |
| --- | --- |
| `aiken.toml` | manifest: project name, compiler version, Plutus version, dependencies |
| `validators/` | `*.ak` files containing validators — the on-chain code |
| `lib/` | shared modules imported by validators and tests |
| `tests/` | optional home for test-only modules; tests are declared with the `test` keyword in any module and collected by `aiken check` |
| `plutus.json` | CIP-57 blueprint produced by `aiken build` |
| `build/` | build cache and downloaded packages |
| `README.md` | project description generated by the scaffold |

## Everyday commands

| Command | What it does |
| --- | --- |
| `aiken check` | compiles everything, runs all tests, prints mem/cpu per test |
| `aiken build` | compiles validators for deployment and writes `plutus.json` |
| `aiken blueprint convert > hello.script` | exports a compiled script for use with cardano-cli |
| `aiken add <owner>/<pkg>` | adds or updates a package dependency |

```bash
aiken check
aiken build
aiken blueprint convert > hello.script
```

`aiken check` is the development heartbeat: it fails on compile errors and on failing tests, and its report doubles as a benchmark because every test shows its memory and CPU execution units. Flags such as `-m` (run a subset of tests) and `--trace-level` exist — run `aiken check --help` for the current set.

## Packages

`aiken new` installs the standard library automatically (`aiken-lang/stdlib` in `aiken.toml`). Add further packages with `aiken add`, for example the fuzzing library used for property tests:

```bash
aiken add aiken-lang/fuzz --version v3
```

Older CLI versions used `aiken packages add ...`; dependency names, versions and sources are recorded in `aiken.toml` under `[[dependencies]]`. Package compatibility tables live in each package's repository, so follow the current docs rather than copying version numbers from tutorials.

## The Playground (Playa)

https://play.aiken-lang.org is Aiken's browser playground. It is the fastest way to try a language construct or a small function with no local setup, and it is useful while reading the documentation. It is not a replacement for a project: dependencies, multi-file layouts and your real test suites live locally.

## From blueprint to off-chain code

`aiken build` writes `plutus.json`, a CIP-57 blueprint. Abridged, it looks like:

```json
{
  "preamble": { "title": "hello-world", "compiler": { "version": "..." } },
  "validators": [
    {
      "title": "hello_world.spend",
      "description": "",
      "compiledCode": "5901...00",
      "hash": "9f3..."
    }
  ]
}
```

| Field | Meaning | Used for |
| --- | --- | --- |
| `compiledCode` | the serialized Plutus Core program | embedding in off-chain code and deriving the script address |
| `hash` | hash of the compiled script | identifying the script without shipping the full code |
| `arguments` | parameters of a parameterised validator | re-hashing per instance to get the instance's address |

Off-chain code (Mesh, PyCardano, cardano-cli) takes `compiledCode`, computes the script credential from it, and derives the script address for your chosen network. Because the hash covers the compiled program, changing validator code changes the address — redeploying is a new script, not an edit of the old one.
